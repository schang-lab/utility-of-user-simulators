# Assistant RL Training with User Simulators

Multi-turn GRPO training of LLM assistants against different user simulators, with a reward from LLM judges, plus the cross-simulator evaluation. In each simulated conversation the simulator plays the user (conditioned on a WildChat intent the assistant never sees) and the assistant responds. The conversation ends when the simulator emits `<|endconversation|>` or after five assistant turns. Two judges then score the whole conversation, and the reward is their mean score divided by ten.

Training runs on a trimmed copy of [SkyRL](https://github.com/NovaSky-AI/SkyRL) in [SkyRL/](SkyRL/). It adds the user-simulator environments and launch scripts and makes small logging changes; see [SkyRL/README.md](SkyRL/README.md) for the full list. For more details, please refer to Section 4.1 and Appendices D–F of our paper.

## User simulators

| `SIMULATOR` | Paper | Environment | Default simulator model | First user turn | Persona guideline |
|---|---|---|---|---|---|
| `sftuser` | SFTUser | `sftuser` | [`jjssuh/sftuser-base-Qwen2.5-14B-Instruct`](https://huggingface.co/jjssuh/sftuser-base-Qwen2.5-14B-Instruct) | real WildChat opening | n/a |
| `rpuser1` | RPUser1 | `rpuser` | `Qwen/Qwen2.5-14B-Instruct` | generated by the simulator | default |
| `rpuser2` | RPUser2 | `rpuser` | `Qwen/Qwen2.5-14B-Instruct` | real WildChat opening | default |
| `rpuser3` | RPUser3 | `rpuser_persona` | `Qwen/Qwen2.5-14B-Instruct` | real WildChat opening | sampled per conversation |

In RPUser3, the persona is drawn from a per-example seed, so all rollouts in a GRPO group face the same persona.

## Installation

Requires CUDA 12.8 and [uv](https://docs.astral.sh/uv/); uv installs Python 3.12 and the pinned dependencies (torch 2.8, vLLM 0.11).

```bash
cd SkyRL/skyrl-train
uv sync --extra vllm
```

The launch scripts call `uv run --isolated --extra vllm`, which reuses this lockfile.

The prebuilt `flash-attn==2.8.3` wheel needs glibc 2.32 or newer. On older systems, build flash-attn from source and point the `flash-attn` requirement of the `vllm` extra in `SkyRL/skyrl-train/pyproject.toml` to your wheel (`"flash-attn @ file:///path/to/flash_attn-....whl"`), then run `uv lock`.

`prepare_data.py` only needs pandas and pyarrow (`pip install -r requirements.txt`), or run it with `SkyRL/skyrl-train/.venv/bin/python`.

## Usage

### 1. Prepare data

RL reuses the user-level train/val/test splits from [sftuser_training](../sftuser_training/README.md), so test conversations are held out from both simulator SFT and assistant RL. Run steps 1–2 of that pipeline first, then:

```bash
python prepare_data.py \
    --input_dir ../sftuser_training/data_with_intents \
    --intent_model Qwen--Qwen3-32B \
    --output_dir ~/data/user_simulator_rl
```

This writes `train.parquet`, `val.parquet`, `test.parquet`, and `sampled_val.parquet`. The last is a fixed 10K subset of val, used for validation during training. One set of files serves every simulator.

### 2. Serve the frozen models

The user simulator and the two judges run as OpenAI-compatible vLLM servers. The scripts expect them on ports 8002–8004 (`USER_URL`, `JUDGE1_URL`, `JUDGE2_URL`). A layout for one 8-GPU node, with the assistant on GPUs 0–1:

```bash
cd SkyRL/skyrl-train
# User simulator: the SFTUser checkpoint, or Qwen/Qwen2.5-14B-Instruct for RPUser1-3.
CUDA_VISIBLE_DEVICES=2,3 uv run --extra vllm vllm serve jjssuh/sftuser-base-Qwen2.5-14B-Instruct \
    --tensor-parallel-size 2 --max-model-len 32768 --port 8002
# Judges, queried at temperature 0 with JSON-schema constrained decoding (Appendix E).
CUDA_VISIBLE_DEVICES=4,5 uv run --extra vllm vllm serve mistralai/Mistral-Small-3.1-24B-Instruct-2503 \
    --tensor-parallel-size 2 --max-model-len 32768 --port 8003
CUDA_VISIBLE_DEVICES=6,7 uv run --extra vllm vllm serve Qwen/Qwen3-32B \
    --tensor-parallel-size 2 --max-model-len 32768 --port 8004
```

Model names in requests must match what each server exposes (by default, the path passed to `vllm serve`). If you serve a local checkpoint, set `USER_MODEL` (and `JUDGE1_MODEL` / `JUDGE2_MODEL`) to that path, or use `--served-model-name`. An SFTUser checkpoint must ship the tokenizer with the `<|endconversation|>` token, as the released checkpoints do (`USER_TOKENIZER` overrides it).

### 3. Train

```bash
cd SkyRL/skyrl-train
export WANDB_API_KEY=...        # or LOGGER=console
CUDA_VISIBLE_DEVICES=0,1 SIMULATOR=sftuser DATA_DIR=~/data/user_simulator_rl \
    bash examples/user_simulator/run_train.sh
```

| Variable | Default | Meaning |
|---|---|---|
| `SIMULATOR` | `sftuser` | `sftuser`, `rpuser1`, `rpuser2`, or `rpuser3` |
| `AGENT_MODEL` | `Qwen/Qwen2.5-3B-Instruct` | Initial assistant |
| `NUM_GPUS` | `2` | GPUs for the assistant (training and rollouts are colocated) |
| `USER_MODEL`, `USER_URL` | see table above, `http://localhost:8002/v1` | User simulator server |
| `JUDGE1_MODEL`, `JUDGE1_URL` | `mistralai/Mistral-Small-3.1-24B-Instruct-2503`, `http://localhost:8003/v1` | First judge |
| `JUDGE2_MODEL`, `JUDGE2_URL` | `Qwen/Qwen3-32B`, `http://localhost:8004/v1` | Second judge |
| `JUDGE_RUBRIC` | `paper` | Judge rubric; see [Judge rubrics](#judge-rubrics) |
| `DATA_DIR` | `~/data/user_simulator_rl` | Output of `prepare_data.py` |
| `OUTPUT_DIR` | `~/ckpts/user_simulator_rl/$RUN_NAME` | Checkpoints (`ckpts/`) and HF exports (`exports/`) |
| `LOGGER` | `wandb` | `wandb`, `console`, or `tensorboard` |

Arguments after the script name are passed to Hydra as extra overrides and applied last. The script pins the Appendix F.2 settings:
- GRPO with batch size 64 and 5 rollouts per prompt.
- Mini-batch 16 (four updates per step).
- Fixed learning rate 8e-7, gradient clipping at 1.0.
- KL loss with the k3 estimator, coefficient 1e-3.
- Symmetric ratio clip of 0.2.
- Assistant responses of up to 2,048 tokens at temperature 1.0; the same sampling is used for validation.

Validation on `sampled_val` and checkpointing happen every 20 steps. HF-format weights for each validated step are written to `$OUTPUT_DIR/exports/global_step_N/policy`. As in the paper, pick the checkpoint at the onset of the validation-reward plateau (`eval/all/avg_score`).

To keep the simulated conversations, add `generator.user_simulator_log_path=$OUTPUT_DIR/logs/user_simulator.jsonl` and `generator.llm_judge_log_path=$OUTPUT_DIR/logs/judge.jsonl` (and `generator.rollout_log_path=...` for token-level rollouts). These logs grow by tens of MB per step.

### 4. Cross-simulator evaluation

Pair a trained assistant with any simulator on the held-out test split, using the same sampling and judges:

```bash
CUDA_VISIBLE_DEVICES=0,1 SIMULATOR=sftuser DATA_DIR=~/data/user_simulator_rl \
    AGENT_MODEL=~/ckpts/user_simulator_rl/rpuser3--Qwen2.5-3B-Instruct/exports/global_step_N/policy \
    OUTPUT_DIR=~/evals/rpuser3-trained_vs_sftuser \
    bash examples/user_simulator/run_eval.sh
python ../../summarize_eval.py ~/evals/rpuser3-trained_vs_sftuser/dumped_evals/eval_only
```

`run_eval.sh` prints the mean reward and dumps every scored conversation. `summarize_eval.py` reports it on the 0–100 scale with a bootstrap CI. For held-out learned simulators such as SFTUser-WC-4.8M, use `SIMULATOR=sftuser USER_MODEL=jjssuh/sftuser2-base-Qwen2.5-14B-Instruct`.

### Judge rubrics

By default the judges use the Appendix E rubric (`JUDGE_RUBRIC=paper`). [judge_rubrics.py](SkyRL/skyrl-gym/skyrl_gym/envs/user_simulator/judge_rubrics.py) also contains alternative rubrics written while developing this work. Each comes with its own JSON schema and score scale, and its reward is normalized to [0, 1].

| `JUDGE_RUBRIC` | Rubric |
|---|---|
| `paper` | Appendix E (default): 0–10 helpfulness scale |
| `v0_0_unit_scale` | Appendix E criteria on a 0.0–1.0 scale |
| `v0_0` | Appendix E, worded as evaluating "the follow-up conversation" |
| `v0_1_initial` | `v0_0` with an explicit 1–10 Likert instruction |
| `v0_1` | `v0_0` asking the judge to be critical and to reserve 10 for perfect responses |
| `v0_2` | Lists weaknesses before scoring; a substantive weakness caps the score at 7 |
| `v0_3` | Weakness-anchored: 0 for any failure, 1–4 by weaknesses, 5–10 by added value if none |
| `v0_4` | `v0_3` with a separate list of value-adds |
| `v0_5` | `v0_4` with an addresses-intent gate and at most three tagged weaknesses |
| `v0_6` | `v0_5` with explicit tests for substantive weaknesses |
| `v0_7` | Mechanical scoring: 0–5 base from tagged weaknesses plus 0–5 bonus from value-adds |

### Other configurations in the paper

- **Assistant size and family** (Section 4.2): `AGENT_MODEL=Qwen/Qwen2.5-1.5B-Instruct`, `Qwen/Qwen2.5-7B-Instruct`, or `meta-llama/Llama-3.2-3B-Instruct` (raise `NUM_GPUS` for larger models).
- **Scaled learned simulators** (Section 4.3): `SIMULATOR=sftuser USER_MODEL=jjssuh/sftuser-base-Qwen2.5-7B-Instruct` or `jjssuh/sftuser-base-Qwen2.5-32B-Instruct`.
- **Scaled role-playing simulators** (Section 4.3): `SIMULATOR=rpuser3 USER_MODEL=Qwen/Qwen3-14B` or `Qwen/Qwen3-32B`. Qwen3 simulators and judges are queried with thinking disabled.
